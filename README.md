# GophKeeper — менеджер паролей

Дипломный проект курса «Go-разработчик» Яндекс Практикума. Техническое задание — в [SPECIFICATION.md](SPECIFICATION.md).

GophKeeper — клиент-серверная система для хранения логинов и паролей, текстов, файлов, банковских карт и генераторов одноразовых паролей. К любой записи можно приложить произвольную текстовую метаинформацию: сайт, банк, человек, список кодов активации.

Секреты шифруются на клиенте ключом, выведенным из мастер-пароля. Сервер хранит только шифротекст, синхронизирует его между устройствами владельца и не может его прочитать: ни мастер-пароля, ни ключа шифрования он не видит.

| | |
|---|---|
| **Клиент** | CLI для Linux, macOS и Windows и TUI на Bubble Tea; работает офлайн и синхронизируется, когда сервер доступен |
| **Сервер** | gRPC (бинарный протокол, protobuf), REST-шлюз grpc-gateway, описание API в Swagger |
| **Хранилище** | PostgreSQL на сервере (или память — для быстрой пробы), bbolt на клиенте |
| **Типы записей** | `credentials`, `text`, `binary` (до 8 МиБ), `card`, `otp` (TOTP, RFC 6238) |

## Быстрый старт

```sh
make run-server       # сервер с данными в памяти: gRPC на localhost:3200, REST на localhost:3201
make build-client     # клиент в bin/gophkeeper
```

В другом терминале:

```sh
./bin/gophkeeper register --login alice     # мастер-пароль спросит дважды
./bin/gophkeeper add credentials --name GitHub --login alice --meta "github.com, рабочий"
./bin/gophkeeper add card --name Visa --number "4111 1111 1111 1111" --expiry 12/30 --cvv 123
./bin/gophkeeper add otp --name "GitHub 2FA" --uri "otpauth://totp/GitHub:alice?secret=JBSWY3DPEHPK3PXP"
./bin/gophkeeper list
./bin/gophkeeper show github --reveal
./bin/gophkeeper otp "github 2fa"
./bin/gophkeeper tui
```

По умолчанию клиент идёт на `localhost:3200`; другой сервер задаётся один раз при входе, `--server host:port`, и запоминается в сессии. С PostgreSQL сервер поднимается через `make run-server-db` или `make docker-up` (Docker Compose), с TLS — через `make certs && make run-server-tls`; тогда при входе клиенту нужен `--ca-cert certs/ca.pem`.

`make help` показывает все цели.

## Клиент

### Команды

| Команда | Назначение |
|---|---|
| `register [-l login]` | регистрация и сразу вход; мастер-пароль не короче 8 символов спрашивается дважды |
| `login [-l login]` | вход и синхронизация |
| `logout` | удалить с устройства токен и ключ; локальное хранилище остаётся зашифрованным |
| `status` | кто вошёл, сколько записей и сколько изменений ещё не отправлено |
| `sync` | отправить локальные изменения и получить изменения с других устройств |
| `list [-t type]` | список записей (без секретов) |
| `show <ref> [-r] [-o file]` | запись целиком; секреты скрыты без `--reveal`; файл сохраняется через `--out` (`-` — в stdout) |
| `otp <ref>` | текущий одноразовый код: код — в stdout, срок действия — в stderr |
| `add <type> -n name ...` | добавить запись: `credentials`, `text`, `binary`, `card`, `otp` |
| `edit <ref> ...` | изменить запись; меняются только переданные флаги её типа |
| `delete <ref>` | удалить запись на всех устройствах |
| `tui` | интерактивный терминальный интерфейс |
| `version` или `--version` | версия, дата сборки и коммит бинарника |

`<ref>` — ID записи, его начало (как в `list`) или имя без учёта регистра. Если подходит несколько записей, клиент перечислит их и попросит уточнить.

Флаги типов (подробно — `gophkeeper add <type> --help`):

| Тип | Флаги |
|---|---|
| все | `--name`, `--meta` |
| `credentials` | `--login`, `--password` (без флага или с `-` пароль спрашивается без эха) |
| `text` | `--text` (`-` читает текст из stdin) |
| `binary` | `--file` |
| `card` | `--number` (проверяется алгоритмом Луна), `--holder`, `--expiry` (MM/YY), `--cvv` |
| `otp` | `--uri otpauth://...` или `--secret` (base32), `--issuer`, `--account`, `--algorithm`, `--digits`, `--period` |

После каждого изменения клиент сразу синхронизируется. Если сервер недоступен, изменение остаётся на устройстве и уйдёт со следующей синхронизацией; `--offline` отключает попытку.

Пароль читается из терминала без эха, а если stdin не терминал — строкой из stdin, поэтому клиент можно использовать в скриптах: `echo "$PASSWORD" | gophkeeper login -l alice`.

### Глобальные флаги

| Флаг | Переменная окружения | Назначение | По умолчанию |
|---|---|---|---|
| `--server` | `GOPHKEEPER_SERVER` | адрес сервера для `register` и `login` | `localhost:3200` |
| `--ca-cert` | `GOPHKEEPER_CA_CERT` | PEM-сертификат CA сервера | системные CA |
| `--insecure` | `GOPHKEEPER_INSECURE` | подключение к удалённому серверу без TLS, только для отладки | выключено |
| `--data-dir` | `GOPHKEEPER_DATA_DIR` | каталог сессии и хранилищ | каталог настроек ОС + `gophkeeper` |
| `--offline` | — | не синхронизироваться после изменения | выключено |

Каталог настроек ОС: `~/.config` в Linux, `~/Library/Application Support` в macOS, `%AppData%` в Windows. В нём лежат `session.json` (права 0600) и `vaults/<хеш сервера и логина>.db` — у каждой учётной записи своё хранилище.

### TUI

`gophkeeper tui` открывает экран входа (или сразу список, если сессия есть) и синхронизируется в фоне после каждого изменения.

| Экран | Клавиши |
|---|---|
| вход | `tab` — поле, `enter` — дальше/войти, `ctrl+r` — регистрация, `esc` — выход |
| список | `enter` — открыть, `n` — новая запись, `e` — изменить, `d` — удалить, `s` — синхронизировать, `/` — фильтр, `q` — выход |
| запись | `r` — показать секреты, `e`, `d`, `w` — сохранить файл, `esc` — назад |
| форма | `tab`/`shift+tab` — поле, `ctrl+s` — сохранить, `esc` — отмена |

Код OTP на экране записи обновляется каждую секунду вместе с обратным отсчётом. Фильтр ищет по имени, типу и метаинформации, но не по секретам.

## Сервер

| Флаг | Переменная окружения | Назначение | По умолчанию |
|---|---|---|---|
| `-a` | `GRPC_ADDRESS` | адрес gRPC-сервера | `localhost:3200` |
| `-http` | `HTTP_ADDRESS` | адрес REST-шлюза и Swagger, `-http ""` выключает шлюз | `localhost:3201` |
| `-d` | `DATABASE_DSN` | строка подключения к PostgreSQL | данные в памяти |
| `-k` | `AUTH_KEY` | ключ подписи токенов | случайный при каждом запуске |
| `-token-ttl` | `TOKEN_TTL` | срок жизни токена | `24h` |
| `-tls-cert`, `-tls-key` | `TLS_CERT`, `TLS_KEY` | сертификат и ключ сервера; оба включают TLS для gRPC и шлюза | без TLS |

Переменная окружения важнее флага. Без `DATABASE_DSN` данные живут в памяти до перезапуска, без `AUTH_KEY` токены перестают действовать после перезапуска — об обоих сервер предупреждает в логе. Миграции схемы встроены в бинарник и применяются при старте. Сервер логирует каждый вызов (метод, код, длительность, адрес клиента), но не тела сообщений.

`make docker-up` поднимает сервер с PostgreSQL в Docker Compose; ключ подписи берётся из переменной `AUTH_KEY` окружения.

## Протокол

Основной протокол — gRPC, описание — [api/proto/gophkeeper/v1/gophkeeper.proto](api/proto/gophkeeper/v1/gophkeeper.proto). Тот же API доступен как REST через grpc-gateway, встроенный в сервер. Его описание в формате Swagger (OpenAPI 2.0) генерируется из proto: [api/openapi/gophkeeper.swagger.json](api/openapi/gophkeeper.swagger.json). Работающий сервер отдаёт его на `/swagger.json` и показывает в Swagger UI на `/docs`.

| gRPC | REST | Назначение |
|---|---|---|
| `AuthService.Register` | `POST /api/v1/auth/register` | регистрация, возвращает токен |
| `AuthService.Login` | `POST /api/v1/auth/login` | вход, возвращает токен |
| `ItemService.CreateItem` | `POST /api/v1/items` | новая запись; ID выбирает клиент |
| `ItemService.UpdateItem` | `PUT /api/v1/items/{id}` | новые данные записи при совпадении версии |
| `ItemService.DeleteItem` | `DELETE /api/v1/items/{id}?version=N` | удаление (запись становится «надгробием») |
| `ItemService.GetItem` | `GET /api/v1/items/{id}` | одна запись |
| `ItemService.ListItems` | `GET /api/v1/items?sinceVersion=N` | поток изменений после версии N, по одному сообщению на запись |

Методы `ItemService` требуют токен в метаданных `authorization` (в REST — заголовок `Authorization: Bearer <token>`). Ошибки: `InvalidArgument` (400) — неверный запрос, `Unauthenticated` (401) — неверные учётные данные или токен, `NotFound` (404) — нет записи, `AlreadyExists` (409) — логин или ID заняты, `Aborted` (409) — запись изменилась с другого устройства.

Запись на сервере — это ID (UUID), тип, зашифрованные данные, версия, признак удаления и время изменения. Предельный размер данных — 12 МиБ, gRPC-сообщения — 13 МиБ.

## Безопасность

- **Мастер-пароль не покидает устройство.** Клиент выводит из него мастер-ключ: Argon2id (1 проход, 64 МиБ, 4 потока) с солью SHA-256(`"gophkeeper:" + логин`) — соль вычисляется на любом устройстве без запроса к серверу. Из мастер-ключа через HMAC-SHA256 получаются два независимых ключа: ключ аутентификации и ключ шифрования.
- **Сервер знает только ключ аутентификации** — он передаётся вместо пароля — и хранит его bcrypt-хеш. Восстановить из него мастер-пароль или ключ шифрования нельзя.
- **Секреты шифруются AES-256-GCM** со случайным nonce. Имя записи и метаинформация шифруются вместе с секретом. ID и тип записи привязаны к шифротексту как associated data, поэтому сервер не может незаметно подменить данные одной записи данными другой. В открытом виде сервер видит только логин, ID и типы записей, их размеры, версии и время изменения.
- **Транспорт** — TLS 1.2+ для gRPC и шлюза (`make certs` выпускает локальный CA и сертификат для `localhost`). К удалённому серверу клиент подключается только по TLS и проверяет сертификат по системным CA или по `--ca-cert`. Без TLS он подключается лишь к серверу на этой же машине (`localhost`, `127.0.0.1`, `::1`), где трафик не покидает компьютер, или к любому — с явным `--insecure` для отладки.
- **Токены** — JWT HS256 со сроком жизни; алгоритм зафиксирован при проверке, так что токен с `alg: none` не пройдёт. Сообщение о неверных учётных данных не различает «нет такого логина» и «неверный пароль».
- **На устройстве** хранилище содержит только шифротекст. Ключ шифрования лежит в `session.json` с правами 0600, чтобы команды CLI не спрашивали мастер-пароль каждый раз; `logout` удаляет его вместе с токеном. Файлы, сохранённые из записей, тоже создаются с правами 0600.
- **Ограничения.** Мастер-пароль нельзя восстановить: забыли — данные потеряны. Сменить мастер-пароль или логин (он входит в соль) пока нельзя. HOTP не поддерживается: его счётчик пришлось бы синхронизировать при каждом коде.

## Синхронизация

У каждого пользователя на сервере есть счётчик ревизий. Любая запись изменения (создание, правка, удаление) увеличивает его в той же транзакции и получает новое значение как версию. Блокировка строки пользователя выстраивает изменения одного пользователя в очередь, поэтому версии фиксируются строго по возрастанию, и запрос «всё, что изменилось после версии N» не пропускает ни одного изменения.

Клиент работает с локальной копией и помечает изменённые записи как неотправленные. Синхронизация:

1. **Pull.** Клиент запрашивает поток изменений после курсора — наибольшей версии, которую он уже получил. Удалённые записи приходят «надгробиями», чтобы другие устройства узнали об удалении.
2. **Разбор.** Если запись не менялась локально, применяется серверная версия. Если менялась, а сервер прислал версию новее той, на которой основано локальное изменение, — это конфликт: серверная версия занимает место записи, а локальное изменение сохраняется отдельной записью «*имя* (conflict *дата*)». Ни одно изменение не теряется.
3. **Push.** Неотправленные изменения уходят на сервер с версией, на которой они основаны (оптимистическая блокировка). Если другое устройство успело раньше, сервер отвечает `Aborted`, и клиент повторяет pull и push (до трёх раундов).

Правка побеждает удаление: запись, удалённая на одном устройстве и изменённая на другом, сохраняется. Применение pull в локальном хранилище атомарно вместе с курсором, поэтому прерванная синхронизация просто повторится.

## Тесты

```sh
make test        # все тесты с -race; тесты с PostgreSQL пропускаются
make test-short  # без функциональных тестов, которые собирают бинарники
make test-db     # все тесты, включая PostgreSQL (поднимает её в Docker)
make cover       # покрытие по функциям и общее, с PostgreSQL
make cover-nodb  # то же без PostgreSQL
```

Тесты с базой запускаются, когда задана `TEST_DATABASE_DSN`, и перед каждым тестом очищают таблицы, поэтому `make test-db` гоняет пакеты по очереди (`-p 1`).

- **Юнит-тесты** есть в каждом пакете: репозитории проверяются одним набором тестов на памяти и на PostgreSQL, синхронизация — на двух «устройствах» против настоящего сервисного слоя сервера, OTP — на тестовых векторах RFC 6238, TUI — нажатиями клавиш.
- **Интеграционные тесты** ([test/integration](test/integration)) запускают настоящий сервер и клиентов на нескольких «устройствах»: сценарии нового и существующего пользователя из ТЗ, правки и конфликты, работа без сети через обрывающийся TCP-прокси, а также проверка через REST, что сервер видит только шифротекст и не принимает мастер-пароль.
- **Функциональные тесты** собирают оба бинарника и гоняют их как пользователь: регистрация, записи, второе устройство, остановка сервера по SIGTERM.
- **Контрактные тесты** сгенерированного шлюза проверяют, что каждый REST-маршрут превращается в нужный gRPC-запрос.

Покрытие по `make cover`: около 94% без сгенерированного кода (около 90% без PostgreSQL). Вместе со сгенерированным кодом protobuf — около 87%. CI ([.github/workflows](.github/workflows)) прогоняет тесты с PostgreSQL, проверяет порог в 70%, собирает клиент под все платформы и запускает statictest Практикума.

## Сборка

```sh
make build                          # сервер и клиент в bin/
make dist                           # клиент для linux, darwin и windows (amd64, arm64) в dist/
make build BUILD_VERSION=v1.0.0     # с явной версией
```

Версия, дата сборки и коммит задаются через `-ldflags` (`main.buildVersion`, `main.buildDate`, `main.buildCommit`); `make` подставляет `git describe`, текущую дату в UTC и короткий хеш коммита, без них выводится `N/A`. Клиент печатает их по `gophkeeper version`, сервер пишет в лог при старте. Клиент собирается без cgo, поэтому кросс-компиляция не требует C-компилятора.

### Генерация кода из proto

Сгенерированный код лежит в репозитории, перегенерировать его нужно только после изменения proto:

```sh
make tools   # плагины protoc фиксированных версий в bin/tools
make proto   # нужен protoc: пакет protobuf-compiler или https://github.com/protocolbuffers/protobuf/releases
```

Зависимости proto (`google/api` для HTTP-аннотаций и опции `protoc-gen-openapiv2`) лежат в `api/proto` рядом с описанием протокола.

### Ключевые решения

- **Шифрование на клиенте.** Сервер — хранилище непрозрачных данных: компрометация сервера или базы не раскрывает секреты. Ценой стала невозможность восстановить мастер-пароль и искать по содержимому на сервере.
- **Два ключа из одного пароля.** Один мастер-пароль удобен пользователю, а разделение через HMAC не даёт серверу, знающему ключ аутентификации, получить ключ шифрования.
- **Версии вместо времени.** Синхронизация опирается на монотонный счётчик пользователя, а не на часы устройств, поэтому не зависит от их расхождения и не теряет изменения при параллельной записи.
- **Офлайн прежде всего.** Изменения сначала сохраняются локально, синхронизация — отдельный шаг. Клиент работает без сети, а конфликт разрешается без потерь — копией.
- **Поток в ListItems.** Записи с файлами бывают большими, поэтому изменения отдаются по одной в server-streaming вызове, а не одним сообщением на весь список.
- **gRPC и REST из одного описания.** Шлюз обращается к gRPC-серверу по сети, как обычный клиент, поэтому у обоих протоколов одни и те же обработчики, проверка токена и логи, а Swagger всегда соответствует коду.
- **bbolt на клиенте.** Встраиваемое хранилище на чистом Go с транзакциями и блокировкой файла: клиент собирается под любую ОС без cgo, а пока хранилище открыто в TUI, команда CLI не испортит его, а получит понятную ошибку.
- **Хранилище в памяти на сервере.** Оно повторяет поведение PostgreSQL (это проверяют общие тесты) и позволяет запустить сервер и все тесты клиента без базы.
